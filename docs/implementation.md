# 実装構成

更新日：2026-11-01。

チーム内で運用しやすい構成にまとめる。設計書の機能を、2つのコンテナと1つの保存領域で提供する。

| 項目 | 実装方式 |
|---|---|
| Web 画面 | React + TypeScript。API から配信する。 |
| API | FastAPI。共有パスワード、セッション、CSRF。 |
| ワーカー | 単一 Python プロセス。SQLite の永続ジョブを順番に処理する。 |
| Wiki | Markdown、索引、履歴、原資料の写しを Git で管理する。 |
| 公開版 | Git commit ID を SQLite に保存する。画面と出力は同じ版を読む。 |
| 一覧 | 公開版の Markdown を読み、メモリにキャッシュする。 |
| 排他 | 単一ワーカーとファイルロックを使う。 |
| 再起動 | 処理中のジョブを待機へ戻して再開する。反映済みジョブを照合する。 |
| Gitea | 設定済み HTTPS 接続から Git を取得する。署名付き Webhook と定期照合を使う。 |
| LiteLLM | `/v1/chat/completions`、tool calling、JSON の応答を利用する。 |
| 予定変更 | 変更案を作成し、適用時に原資料と Wiki へ記録する。 |
| 所感・困りごと | 話者・対象者・記録者・時点・出典を関連付ける。 |
| 出力 | ガント、Excel、Markdown の業務報告。 |
| バックアップ | コンテナ停止中に原資料、Git、SQLite をまとめる。 |
| 文章 | 日本語の本文を簡潔な肯定文へ統一する。引用とコードは原文を保つ。 |

利用者 ID は単一所有者、内部 ID は UUID、予定試算は暦日を使う。初期版の接続設定は `.env` で管理する。

取り込みの最終結果は `finish_result` ツールで受け取る。公開前に引用、日付、関連ページと人物・案件の参照、発言の性質を検査し、修正点をモデルへ返す。説明文に JSON が含まれる場合は、その JSON を読み取る。通常の文章で応答した場合は、JSON への整形を追加で依頼する。

補正は JSON 応答を使い、元の入力、読んだ資料、修正対象のページ案、検査結果を渡す。検査で指定したページの変更を受け付け、作成済みのページ案を保持する。全体の検査を通った結果を公開する。

予定終了日が登録された進行中のタスクは、締め切りが未定なら確認事項を作成する。日付の確認にはカレンダーで回答し、選択した日付と出典を対象タスクへ直接反映する。追記で日付が省略された場合は登録済みの値を保持する。対象タスクと項目で重複をまとめ、回答済みの確認事項の状態を保つ。

原案の詳細設計は [詳細設計書](detailed-design.md)、実装の起動と接続は [接続ガイド](connections.md)、検証は [テスト手順](testing.md)に記載する。

## 同じノートへの追記

既存ノートの追記は Git 差分の追加行から更新内容を抽出する。モデルへ既存ページの ID・関連・確定済みの日付を渡し、対象ページの変更値と追記文を JSON Schema で受け取る。新しい案件や人物などが登場した場合は、原資料を読む通常の Wiki 整理へ進む。

アプリは既存本文と引用を保持し、記録日を付けて新しい事実を追記する。タスクの状態と困りごとの解決状況を更新し、明示された変更のある日付を反映する。引用は今回の追記の原文と照合する。保存後は同じノートの最新 commit を同期位置として記録する。

相談でガントの表示や報告の作成が完了したら、画面のリンクを返す。案件名は保存された案件 ID に解決し、一覧と出力を同じ範囲へ絞る。

初回の原資料が各 24,000 文字以内のときは、全文を渡して JSON Schema でページを生成する。人物・案件・タスクなどの必須項目と引用元 ID を指定する。大きな原資料と既存 Wiki への追加では、原資料と関連ページをツールで読みながら整理する。保存前に必須項目、参照先、引用を検査する。

短い原資料の引用は、原文の行から選ぶ。ノートの追記も同じ方法で引用を選び、出典の ID と本文を保存前に照合する。
