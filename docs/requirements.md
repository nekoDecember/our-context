# 要件定義書

対象：Our Context（仮称）。版：0.1。作成日：2026-11-01。状態：設計原案。実装方式は [実装構成](implementation.md)に記載する。

## 1. 目的と背景

チームでは Redmine を使い、個人の細かな作業は Obsidian に記録している。日々の記録を報告用に書き直す負担があり、進捗の転記が後回しになりやすい。既存の Gitea と LiteLLM を使い、普段のメモから業務の文脈を継続して整理し、相談・予定整理・報告へつなげる。

本アプリは、Karpathy の LLM Wiki をタスク・プロジェクト・チームの実務に適用する。Wiki の整理原理を独自に作り直すことは目的に含めない。

日々の入力は作業だけに限定しない。会議で得た背景、判断理由、合意、懸念、誰かの困りごと、本人や他のメンバーの所感も、メモに記載された範囲で保存・参照できるようにする。

最終的には、複数の情報源から「誰が今何に困っているか」「メンバーがどう受け止めているか」まで広く把握できる状態を目指す。初期版は、そのための情報の出所と人物への関連付けを備える。

## 3. 利用者と情報の範囲

### 3.1 初期版の利用者

利用者は自分 1 人とする。チーム、プロジェクト、人物は、業務コンテキストの対象として扱う。チームメンバー自身のログイン、回答の依頼、外部への通知や送信は初期版に含めない。

### 3.2 扱う業務コンテキスト

| 対象 | 保存・参照する内容 |
|---|---|
| タスク | 目的、担当、状態、予定、締め切り、完了条件、依存関係、困っていること。 |
| プロジェクト | 目標、優先順位、制約、マイルストーン、決定事項、合意、経緯。 |
| チーム | 体制、責任範囲、相談先、判断者、業務ルール、記録された予定。 |
| 人物 | 明示された担当・関わり、発言、困りごと、所感、その日時と出所。 |
| 共通の業務知識 | システム、顧客、手順、用語、過去の調査・対応など、業務に必要な情報。 |

人物に関する記録は、発言者、対象者、記録者を区別する。「田中さんが困っていると本人が話した」と「自分には田中さんが困っているように見えた」を同じ事実として扱わない。状態には記録時点を伴わせ、古い記録だけで現在の状態を断定しない。

### 3.3 情報源

- 日々追記する Obsidian ノート。
- 同じリポジトリ内で指定した、体制・役割・案件・ルールなどの初期資料。
- 常設ページでの確認事項への回答。
- 常設ページから追加した補足や訂正。
- 利用者が適用した予定・担当・状態の変更。

同じノートへの追記を標準とする。複数の Markdown ファイルも対象パスの指定で扱える。取り込み対象でない Vault の内容は送信しない。

## 4. 運用シナリオ

### UC-01 終業時の記録整理

1. 利用者は、日付を付けた見出しの下に普段どおり記録する。
2. 終業時に commit・push する。日付以外の厳密な入力書式は必須にしない。
3. アプリが未反映の変更を取得し、関連する過去の情報と合わせて Wiki を更新する。
4. 利用者は更新結果、未確定事項、予定を常設ページで確認する。

夜をまたいだ push や過去の日付の訂正も処理する。「push された日の文章だけ」を対象にしない。

### UC-02 文脈を踏まえた相談

利用者が「この遅れはプロジェクト全体に影響するか」と質問する。AI はタスクの依存関係、期限、案件の制約と記録された合意を参照して回答する。不明な条件がある場合は、分かる範囲と確認が必要な条件を示す。

### UC-03 確認事項への回答

AI が「実施日を決めるには、切り替え方式の合意状況を確認したい」と提示する。利用者は回答するか、保留する。回答は新しい情報源として保存し、Wiki と予定に反映する。反映待ち・反映済み・失敗を区別して表示する。

### UC-04 予定の整理とガント

利用者が案件を選び、タスク一覧とガントを見る。日付が未定の作業は別に確認できる。「検証を 2 日遅らせたら」と相談すると、AI が前提と影響する作業を含む変更案を示す。適用した場合に予定が更新される。

### UC-05 報告の作成

利用者が対象案件と期間を選び、進捗、残作業、困りごと、確認事項を Excel または報告文として出力する。Redmine のチケット番号が分かる項目は、チケット単位でもまとめる。

### UC-06 困りごとや所感の記録

利用者が「田中さんは環境構築で詰まっていると話していた」と書く。AI は対象者、困りごとの内容、記録日、出所を関連付ける。対応するタスクがなくても記録できる。後に解決したと分かれば、過去の経緯を残し、現在の整理を更新する。

## 5. 機能要件

優先度は M＝初期版必須、F＝将来拡張とする。

### 5.1 初期設定と取り込み

| ID | 優先度 | 要件 |
|---|---|---|
| FR-01 | M | ワークスペース、自分の役割、チーム体制、進行中の案件、初期ルールを登録できる。未記入項目があっても利用を開始できる。 |
| FR-02 | M | Gitea の対象リポジトリ、ブランチ、ノートのパスを指定できる。初回取り込みの範囲を表示できる。 |
| FR-03 | M | 署名を検証した push 通知を受け、非同期で取り込む。重複通知で同じ処理結果を重複登録しない。 |
| FR-04 | M | 最後に正常反映した版からの変更を処理する。追記・訂正・削除・通常の改名を扱い、原文の過去版を保存する。 |
| FR-05 | M | Web から回答、補足、訂正を追加できる。取り込み失敗時は原文を残し、再実行できる。 |

### 5.2 LLM Wiki と文脈

| ID | 優先度 | 要件 |
|---|---|---|
| FR-06 | M | Karpathy 方式の Wiki 運用に従い、原資料を保全して Wiki を継続更新する。索引、相互参照、出典、更新履歴を維持する。 |
| FR-07 | M | タスク・案件・チーム・人物・共通知識を関連付け、目的、合意、判断、制約、困りごと、所感を扱える。すべての記録をタスクに変換しない。 |
| FR-08 | M | 明示された事実、本人の所感、他者による観察、提案、未確認を区別し、時点と出典を保持する。 |
| FR-09 | M | Wiki を点検して、矛盾、古い情報、リンクの不整合、業務上必要な不足情報を検出する。点検と内容修正を分ける。 |

### 5.3 常設ページと質問回答

| ID | 優先度 | 要件 |
|---|---|---|
| FR-10 | M | ホームで直近の更新、確認事項、困りごと、予定、取り込み状態を確認できる。 |
| FR-11 | M | Wiki を閲覧・検索し、案件・チーム・人物から関連する内容と出典へ移動できる。 |
| FR-12 | M | 全体または選択した案件・チーム・人物の文脈を指定して質問できる。回答に参照した版と出典を付ける。 |
| FR-13 | M | 情報が不足するときは不足を明示する。記録にない担当・期限・合意・人物の状態を確定事項として答えない。 |
| FR-14 | M | 有用な質問回答を利用者が Wiki に残せる。生成された分析と、利用者が補足した事実を区別する。 |

### 5.4 確認事項

| ID | 優先度 | 要件 |
|---|---|---|

| FR-16 | M | 回答、保留、不要の指定ができる。解決済みの質問を理由なく再提示しない。新しい矛盾や状況変化がある場合は再確認できる。 |
| FR-17 | M | 回答を情報源として取り込み、成功時に Wiki と関連表示へ反映する。回答を受け付けただけで反映済みと表示しない。 |

### 5.5 タスク・予定・業務ツール

| FR-19 | M | 常設ガントに予定、締め切り、依存関係を表示する。日付や関係が未確定の項目は、その状態を表示する。 |
| FR-20 | M | 会話またはフォームでタスクの予定・担当・状態の変更案を作成し、利用者が適用できる。影響と前提を確認できる。 |
| FR-21 | M | 質問回答エージェントから、情報検索、ガントの表示条件変更、予定の試算、変更案作成、報告出力を利用できる。 |

| FR-23 | M | 日次・週次の報告文を作成できる。Redmine のチケット番号がある情報は番号別にまとめられる。外部へ自動投稿しない。 |

| FR-25 | M | バックアップと復元の手順を備え、復元後も Wiki と確認事項への回答履歴を使える。 |
| FR-26 | F | 複数メンバーからの直接入力、外部の会話・会議情報の取り込み、共有範囲と権限の管理。 |
| FR-27 | F | Redmine API 連携、既定 Excel テンプレート、通知、カレンダー連携。 |

## 6. 業務ルール

| ID | ルール |
|---|---|
| BR-01 | 個人メモから分かる範囲と、チーム全体の状態を区別する。未記録は不明として扱う。 |
| BR-02 | 担当、完了、合意、締め切りは、明示された記録または利用者の回答に基づいて確定する。 |
| BR-03 | 自分の実施予定と、対外的な締め切り・チームとの約束を別の情報として扱う。 |
| BR-04 | 過去の記録と現在の整理を区別する。訂正・撤回・解決を反映しても過去の根拠は残す。 |
| BR-05 | 人物の同定が曖昧な場合は、別人を自動で統合しない。 |
| BR-06 | 確認事項は、進行・判断・報告への影響があるものを優先する。入力欄を埋めるためだけに質問しない。 |
| BR-07 | AI の分析や推測を、それ自体で独立した事実の根拠にしない。 |
| BR-08 | 原メモ内の指示文で、接続先、処理ルール、ツール権限を変更しない。 |
| BR-09 | 表示、質問回答、ガント、報告の参照版を揃える。更新中も前の完成した版を利用できる。 |

## 7. 非機能要件

以下の数値を初期の設計目標とする。

| ID | 分類 | 要件・目標 |
|---|---|---|
| NFR-01 | 規模 | 初期評価は 1 利用者、20 案件、30 人、1,000 Wiki ページ、1,000 タスクを上限の目安とする。実データで再評価する。 |
| NFR-02 | 応答 | 指定規模の通常一覧・本文表示を、LAN 上で原則 2 秒以内とする。LLM 処理と初回キャッシュ生成は別計測とする。 |
| NFR-03 | 非同期処理 | Webhook はジョブの永続化後に応答し、目標 2 秒以内とする。LLM 完了を待たない。 |
| NFR-04 | 処理予算 | LLM 呼出回数、トークン量、処理時間に上限を設ける。超過時は反映前の状態を保ち、理由を表示する。 |
| NFR-05 | 信頼性 | 再送・再起動・途中失敗で入力を失わず、完成前の Wiki を公開しない。 |
| NFR-06 | データ保全 | アプリが取り込んだ原資料とその版を保存する。復元目標は、日次バックアップから RPO 24 時間・RTO 2 時間を暫定値とする。 |
| NFR-07 | アクセス | LAN 利用でも認証を必要とする。API キーや Git 認証情報をブラウザへ渡さない。 |
| NFR-08 | 画面 | PC を主対象とし、幅 360px でも本文、確認事項、タスク一覧を扱える。ガントには一覧表示を併設する。 |
| NFR-09 | 説明可能性 | 回答と業務情報から、出典、記録時点、参照版へ移動できる。根拠検査と内容の正しさの保証を区別する。 |
| NFR-10 | 保守性 | Wiki の Markdown と原資料を取り出せる。タスクなどの参照用 DB は Wiki から再構築できる。 |
| NFR-11 | 常駐 | ログイン・再起動後も必要なサービスを復帰でき、状態とログを確認できる。 |
| NFR-12 | 到達性 | LAN 利用の完了条件は、実際の LAN IP でページと認証済み API が利用できることとする。ホスト上からの確認と別端末確認を区別する。 |

## 8. 初期版に含めないもの

- メンバー全員のログイン、チームへの回答依頼、個人別の共有範囲管理。
- チャット、会議、メールからの自動収集。
- Redmine への API 接続と投稿。
- 既存 Excel 書式への自動転記。
- チーム全体の空き時間を把握した自動的な人員配置・日程確定。
- ガント上のドラッグ操作による予定編集。
- 画像、PDF、Office ファイルの取り込み。これらは後から情報源を追加する拡張対象とする。

| AC-10 | 回答の反映 | 回答が原資料として保存され、取り込み成功後に Wiki と関連する予定に反映される。 | FR-05, FR-17 |

| AC-13 | 出力 | Excel と報告文が同じ参照版・対象期間を使い、未確定の情報を確定と表現しない。 | FR-22, FR-23 |
| AC-14 | 失敗と復旧 | LLM 障害・途中終了後も以前の Wiki を閲覧でき、同じ入力を安全に再実行できる。 | FR-24, NFR-04, NFR-05 |
| AC-15 | 署名・対象制限 | 不正署名、対象外リポジトリ、対象外パスの入力で Wiki が変わらない。 | FR-02, FR-03, BR-08 |
| AC-16 | 認証・LAN | 未認証 API は拒否され、LAN IP でページと認証済み API を利用できる。 | NFR-07, NFR-12 |
| AC-17 | 人物の記録 | 本人の発言と利用者の観察を区別し、日付と出典を表示する。未記録の現在状態を推定しない。 | FR-07, FR-08 |
| AC-18 | 矛盾と撤回 | 原資料の削除・撤回、矛盾、循環する依存関係を隠さず、不確定として扱える。 | FR-04, FR-09, FR-13 |
| AC-19 | 取り出しと復元 | バックアップから原資料、公開 Wiki、回答、確認事項の状態を復元し、参照用 DB を再生成できる。 | FR-25, NFR-06, NFR-10 |
| AC-20 | 常設ページ | ホームから案件・人物・出典・予定・質問回答へ移動し、反映待ちと失敗を確認できる。 | FR-10, FR-11, FR-24 |

LLM の文章品質は、代表的な業務メモを使って実際の接続先モデルでも確認する。構文検査や疑似 LLM の試験だけで品質を合格にしない。

## 10. 将来拡張への接続

今後、本人からの困りごと・所感の入力、定例や会議の記録、チームの会話などを情報源として追加できるようにする。初期版から、情報源の種別、発言者・対象者・記録者、時点、チーム・案件との関連を保持する。

複数利用者で共有する段階では、認証と共有範囲を改めて設計し、初期版の個人用データをそのまま全員に公開しない。チーム共有への移行は別の受け入れ条件を持つ。
